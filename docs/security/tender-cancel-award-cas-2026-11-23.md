# Tender cancellation versus concurrent award | 23 November 2026 | DRAFT ONLY

## Evidence and bounded interpretation
On baseline `spot-requirements` commit `38627662a93ab6cd7e35a792a46a62de82010904`, `POST /api/tenders/[id]/cancel` reads the tender in a Serializable transaction, but writes `tender.update({where:{id}})` without rechecking owner, original status and awarded response at the write. PostgreSQL Serializable isolation normally aborts conflicting overlapping writes (`P2034` in Prisma), but the handler previously mapped those to HTTP 500. This patch adds an explicit guarded claim and retryable 409, limiting unsafe drift if transaction semantics change. This is **source-level concurrency hardening**, not a confirmed exploit or proof of a lost award in production.
