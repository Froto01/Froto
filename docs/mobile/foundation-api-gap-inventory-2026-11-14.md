### Current role and confidentiality contract

1. `GUEST_CUSTOMER`: user who owns that guest auction; only that user may inspect all comparable guest bids, award the job and confirm completion. Cannot use guest post route once a company membership exists under current logic.
2. `COMPANY_PROVIDER`: authenticated member of the bidding company; may browse eligible guest opportunities, submit **one sealed bid per company**, inspect **own** bid, and act on an awarded guest job when its company wins. Actual endpoint role granularity/verified-provider eligibility is a separate security review item.
3. Other authenticated individuals/companies must not receive private owner/bid details without an authorized relation. Server is authoritative; UI mode toggles must not grant permission.
4. The web `Job` status flow uses **different** buyer/provider action rules; do not generalize its completion semantics to guest customer jobs. Multi-company `companies[0]` behavior needs a coherent active-tenant design and tests before native implementation.

### Proposed shared mobile contract (NOT API implementation)

See [`guest-auction-mobile-contract.v0.json`](./guest-auction-mobile-contract.v0.json), covered by [`guest-auction-mobile-contract.test.mjs`](./guest-auction-mobile-contract.test.mjs). Its `existing` routes map to the pinned website backend; `future` contract requests are design placeholders **not live routes**. The mobile client must use *the same authoritative server records* as the website, never its own parallel job/payment ledger. Until reviewed, native code must not assume that current cookie/web-oriented Clerk configuration or authorization behavior is safe for mobile token requests.

### Device and resilience acceptance (future, not executed)

- Owner creates guest job with valid structured Australian addresses and timezones, optional photos/dimensions/access, receives unique authoritative ID; denied camera/location permissions have manual fallbacks.
- Eligible courier can discover in-coverage jobs, submit a private offer; unrelated companies cannot inspect rivals, owner can compare price/pickup time/company rating/availability.
- Award requires fresh server authority, consistency under two concurrent devices, explicit owner consent, no duplicate award and recoverable receipt after a timeout. Payment is still **sandbox-design-only** until provider/legal and separate owner approval.
- Winning company updates pickup/delivery/proof; customer confirms completion, including issue/no-show/dispute path. Do not treat driver's self-report as customer confirmation.
- Notifications open correct role-scoped record from foreground, background, cold start and signed-out states; no leaked details in lock-screen preview or malicious redirects.
- Test offline retries, expired sessions, multi-company accounts, tenant isolation, AEDT/AEST DST boundaries and location/camera-denial behavior on **physical iOS and Android devices**, plus simulated networks. Every change requires exact branch/SHA, test output, browser/mobile/CI separation.
- Launch scope: AUD, Australian addresses, region-specific coverage and timezones first. Internationalization hooks are future-facing only; country launch and live payments are distinct approvals.

## Shared-codebase choices (proposed evaluation, not owner framework selection)

| Option | Potential advantage for this repository | Trade-offs / decision gate |
| --- | --- | --- |
| **React Native + Expo + TypeScript** (**initial technical preference, NOT approved**) | Aligns with website TypeScript/React team; enables shared *pure* validation/types while keeping server authorization in Next.js. Expo supplies camera/notifications/deep-link libraries and native dev builds. | Still a separate app and native permissions/build signing; web Next.js UI cannot be pasted in. Test real devices, Clerk native session compatibility, notifications, native map/address dependencies and possible EAS costs. Official: https://docs.expo.dev/linking/into-your-app/ and https://docs.expo.dev/develop/development-builds/faq/ |
| **Flutter + Dart** (alternative) | Single iOS/Android codebase and strong mobile controls; platform channels available | Additional Dart stack; less direct type/business-logic reuse from existing React/TypeScript. Native plugins, identity bridge, map/address, push and release processes still needed. Official: https://docs.flutter.dev/platform-integration/platform-channels |
| **Separate Swift + Kotlin** (alternative) | Full native fidelity for advanced features | Highest duplicated iOS/Android code and maintenance burden for first app release. |
| Mobile-first web/PWA wrapper (not preferred for dedicated-app promise) | Potential quick validation of UX | Does **not** automatically satisfy native push, camera/background behavior, store acceptance or real-device checks. |

**Proposed architecture:** separate `apps/mobile` or repository workspace **after** framework decision; shared backend Next.js API, no duplicate DB; pure `packages/contracts` for versioned types/error maps only after server contract and permission reviews; mobile session via approved Clerk native flow, secure token storage and role-scoped API calls; server-side address/geocode, upload and payment services once separately authorized. Current PR adds **none** of those integrations.
